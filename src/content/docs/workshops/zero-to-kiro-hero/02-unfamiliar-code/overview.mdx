**By the end of this act you can:** drop into a codebase you've never seen, use the
agent to map how it works, and make a non-trivial change that *holds* — because you
planned it before touching code.

## The arc

<Steps>

1. **Orient.** Use the agent to explain the codebase and locate where things live.

2. **Plan.** Turn that understanding into an explicit plan before writing code.
   This is where planning earns its keep — and where vibing quietly fails.

3. **Make the change.** Execute against the plan. A test goes green and stays green.

</Steps>

<Aside type="note" title="The change: add a variant to a closed set">
The exercise is to add the next member of an existing closed set (the codebase
already supports two or three of something — you add the next one). Done right, it
threads through several discoverable places. Vibing adds the obvious spot and
misses one, so it compiles but breaks at runtime. Planning enumerates the touch
points first, so it holds.
</Aside>
