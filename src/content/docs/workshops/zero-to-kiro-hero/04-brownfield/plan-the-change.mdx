**Goal:** an explicit plan for making `spent` honest, *before* touching code. This is the spine
of the whole workshop: the plan is the difference between a change that holds and one that
silently breaks.

You'll build the plan two different ways and compare what each surfaces.

## Path A: Spec mode

<Aside type="note" title="Instructor demo: fast, but quiet">
In the Kiro IDE, switch to **Spec mode** and ask: *"Make the spending summary correct."* It runs
to a full spec **without asking you much**, and that's the risk. Given a vague request, it fills
the gaps with *its* assumptions. Watch whether its spec even mentions transfers, refunds, or
pending. Spec mode is excellent when you already know exactly what you want. Here, you don't yet.
</Aside>

## Path B: grill-me-with-docs

<Aside type="caution" title="Requires the skill from Act 1">
This uses the `grill-me-with-docs` skill you installed in [Act 1 · Skills](../../02-context/skills/).
If you skipped it: `npx skills@latest add mattpocock/skills -a kiro-cli`, then restart Kiro.
</Aside>

Run it against the same goal, but specific enough that Kiro can find what to fix — name the
**symptom**, not the fix:

```text
/grill-me-with-docs the spending total in /summary over-counts — make it report the honest number
```

It reads the code **and the project docs you generated with `/code summary`**, then **interrogates
you**, often 10 to 20 questions, until it's sure it understands, and writes the answers into a
decision doc. Naming the symptom only points it at the right code — it still forces the decisions
the prompt left open:

- Does a **transfer** between your own accounts count as spending? *(no)*
- Does a **refund** reduce spending, or get ignored? *(reduce)*
- Do **pending** charges count before they clear? *(no)*

**That's the whole point:** the bug was born from unanswered questions. This drags them into the
light before a single line changes.

## Write the plan down

However you got here, capture the **decisions** and the **touch points**:

<Steps>

1. **Decisions:** transfers excluded, refunds netted, pending excluded, for an honest total of **$850**.
2. **Touch points** (this is what vibing misses): the `transactions` **schema** + **seed** (add a
   `kind` so a transfer is distinguishable), the `/summary` **query**, the `/transactions`
   **output**, and the **tests**.

</Steps>

<Aside type="tip" title="Same destination, different path">
Both paths can reach the same plan. But Spec mode got there only because *you* knew to mention
transfers/refunds/pending, while grill-me got there by *asking*. Neither is "right." Pick the one
that fits how clearly you already understand the change. For an unfamiliar codebase, you usually
want to be grilled.
</Aside>

<Aside type="note" title="Checkpoint">
Everyone has a written plan listing the three decisions **and** the touch points the change
threads through: schema, seed, query, output, tests.
</Aside>
